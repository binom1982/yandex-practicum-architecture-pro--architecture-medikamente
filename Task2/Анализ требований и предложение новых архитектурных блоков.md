# Анализ требований и предложение новых архитектурных блоков

## Новые блоки в архитектуру проектируемой системе С4

**1. Security & Compliance Service (Сервис безопасности и комплаенса)**

* **Критерий:** В ТЗ сказано: «Необходимо определить категории данных пациентов и разнести их по различным доменам... Для каждой категории определить роли (RBAC) или атрибуты (ABAC)». А также: «В системе есть возможность помечать тегами данные».
* **Функция:** Выполняет роль **PDP (Policy Decision Point)** . Централизованно хранит политики доступа (RBAC/ABAC), теги конфиденциальности (разработанные в Задании 1) и согласия пациентов на обработку ПДн (требование 152-ФЗ). Отвечает на запросы от других систем: «Можно ли этому пользователю показать эти данные?».

**2. API Gateway с Data Protection (Шлюз безопасных интеграций)**

* **Критерий:** В ТЗ прямо указано: «Интеграция лаборатории анализов с API. API-контракты должны закрывать и скрывать категории данных... Необходимо предотвратить использование API-контрактов, позволяющих третьим лицам получать данные, которые они не должны видеть».
* **Функция:** Выполняет роль **PEP (Policy Enforcement Point)** для внешних и мобильных каналов. Принимает все входящие запросы (от ЛК пациента, мобильной версии, лаборатории), обращается к *Security & Compliance Service* за правами, и **на лету** маскирует или фильтрует чувствительные поля (например, скрывает диагноз при передаче в лабораторию, оставляя только код анализа).

**3. Secure Analytics Layer (Защищенный аналитический слой на ClickHouse)**

* **Критерий:** В ТЗ есть цель: «создать озеро данных для автоматизации BI, LLM и AI». А в Задании 2 требуется: «Предложить слой, который обеспечивает аналитическую работу с данными с учётом Privacy by Design».
* **Функция:** Это витрина обезличенных данных (Data Mart) на базе **ClickHouse** (он уже есть в стеке техдира). Данные попадают сюда из операционной базы уже **псевдонимизированными** (ФИО заменено на внутренний UUID, даты сдвинуты). Аналитики и ML-модели работают только с этим слоем, что исключает утечку реальных ПДн и врачебной тайны в BI-отчеты.

**4. Retention & Archiving Service (Сервис управления жизненным циклом и архивом)**

* **Критерий:** В ТЗ в разделе НФТ сказано: «Чувствительные данные важно своевременно удалять. Если клиент обратится с запросом, обработку его данных нужно прекратить».
* **Функция:** Реализует право на забвение и юридические требования по срокам хранения (5 лет для бухгалтерии, 25 лет для медкарт). При запросе пациента на удаление данных сервис применяет механизм **Crypto-Shredding** (уничтожает ключ шифрования конкретной записи в KMS) и переносит данные в «холодный» изолированный архив (Legal Hold). По истечении законных сроков хранения данные удаляются физически.
